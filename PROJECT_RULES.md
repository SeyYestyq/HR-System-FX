# Инженерные стандарты разработки HireSystem (Clean Architecture, SOLID & JavaFX)

> **Статус:** Обязательно к соблюдению во всех модулях и классах проекта.  
> **Стек:** Java 21, JavaFX 21, Maven, PostgreSQL 15 (Docker), JDBC, JUnit 5.

---

## 1. Архитектурные принципы и SOLID на практике

### 1.1. Single Responsibility Principle (SRP — Принцип единственной ответственности)
Каждый класс решает строго одну задачу:
* **FXML-контроллеры (`MainController`, `VacancyDialog`):**
  * Отвечают **только** за перехват событий UI (клики, выбор в таблице, открытие модалок) и связывание данных (`CellValueFactory`, `ObservableList`).
  * ❌ **СТРОГО ЗАПРЕЩЕНО:** писать SQL-запросы, вызывать `DriverManager`/`Connection`, рассчитывать бизнес-метрики или валидировать бизнес-правила внутри контроллеров.
* **Сервисный слой (`VacancyService`, `StatisticsService`, `CsvExportService`):**
  * Отвечает **только** за чистую бизнес-логику, валидацию входных данных, координацию CRUD и расчет аналитики.
  * ❌ **СТРОГО ЗАПРЕЩЕНО:** импортировать классы JavaFX (`javafx.scene.*`, `Alert`, `TableView`) в сервисный слой. Сервис должен быть тестируемым без запуска UI.
* **Слой доступа к данным (`PostgresVacancyDao`, `PostgresUserDao`):**
  * Отвечает **только** за работу с базой данных через чистый JDBC (`PreparedStatement`, маппинг `ResultSet` в POJO/Record).
* **Размер классов:** Предпочтительно до **150–200 строк**. Длинные методы (более 25–30 строк) декомпозируются.

### 1.2. Dependency Inversion Principle (DIP — Инверсия зависимостей)
* Взаимодействие между слоями строится **строго через интерфейсы**:
  * `VacancyService` зависит от интерфейса `VacancyDao`, а не от конкретного `PostgresVacancyDao`.
* **Внедрение зависимостей (Constructor Injection):**
  * Все зависимости передаются через конструкторы:
    ```java
    // ПРАВИЛЬНО:
    public VacancyService(VacancyDao vacancyDao) {
        this.vacancyDao = vacancyDao;
    }
    // НЕПРАВИЛЬНО:
    this.vacancyDao = new PostgresVacancyDao(); // Жесткая сцепка запрещена!
    ```

### 1.3. Liskov Substitution (LSP) и параллельная разработка через стабы
* Для параллельной работы UI-разработчика и бэкендера создаётся `InMemoryVacancyDao` (Stub), реализующий интерфейс `VacancyDao`.
* Контроллеры и сервисы должны работать одинаково корректно как со стабом в оперативной памяти, так и с реальной базой PostgreSQL.

### 1.4. Interface Segregation (ISP)
* Не создавайте единый «мега-DAO». Интерфейсы разделены по сущностям: `VacancyDao`, `UserDao`.

## 2. Потокобезопасность и отзывчивость JavaFX (Thread Safety)

1. **Главный поток UI (JavaFX Application Thread) не должен блокироваться:**
   * ❌ **СТРОГО ЗАПРЕЩЕНО:** выполнять сетевые запросы, долгие SQL-запросы, расчет аналитики или экспорт файлов в UI-потоке. Это приводит к зависанию интерфейса («Not Responding»).
2. **Фоновые задачи и асинхронность:**
   * Любые тяжелые операции выполняются в фоновых потоках через `Task<T>`, `CompletableFuture` или сервис `AsyncExecutor`.
3. **Обновление интерфейса:**
   * Любые изменения UI-компонентов из фонового потока выполняются строго через диспетчер JavaFX:
     ```java
     Platform.runLater(() -> {
         statusLabel.setText("Данные загружены");
         tableView.setItems(observableList);
     });
     ```

## 3. Стандарты работы с базой данных и JDBC

1. **Защита от SQL-инъекций:**
   * ❌ Запрещена конкатенация SQL-строк (`"WHERE title = '" + text + "'"`).
   * Использовать **исключительно** `PreparedStatement` с параметрами `?`.
2. **Управление ресурсами (Try-with-resources):**
   * Все объекты `Connection`, `PreparedStatement` и `ResultSet` **обязаны** закрываться через `try-with-resources`:
     ```java
     try (Connection conn = dbManager.getConnection();
          PreparedStatement ps = conn.prepareStatement(SQL_FIND_ALL);
          ResultSet rs = ps.executeQuery()) {
         // маппинг данных
     }
     ```
3. **Никакого хардкода реквизитов:**
   * URL, логин и пароль к PostgreSQL загружаются строго из `src/main/resources/database.properties` через `ConfigLoader`.

## 4. Обработка ошибок, исключения и логирование

1. **Типизированные исключения вместо падений:**
   * Для бизнес-правил: `BusinessException` (например, попытка удалить закрытую вакансию).
   * Для ошибок ввода пользователя: `ValidationException` (пустые обязательные поля, некорректная зарплата).
   * Для сбоев SQL/БД: `DatabaseException` (обёртка над непроверяемым `SQLException`).
2. **Логирование:**
   * ❌ Запрещен вывод через `System.out.println` и `e.printStackTrace()` в рабочем коде.
   * Использовать **SLF4J Logger** (`LoggerFactory.getLogger(...)`).
3. **Диалоги ошибок для пользователя:**
   * Ошибки пользователю показываются через централизованный хелпер `UiUtils.showErrorAlert(...)`, не «роняя» программу.

---

## 5. Регламент приемки кода (Definition of Done)

Перед отправкой кода в общий репозиторий / коммитом:
1. **Сборка и тесты:** Команда `mvn clean test` выполняется успешно без ошибок.
2. **Юнит-тесты:** Сервисный слой покрыт тестами на JUnit 5 + AssertJ (позитивные сценарии и валидация).
3. **Чистота кода:** Отсутствуют неиспользуемые импорты, закомментированные куски старого кода и временные заглушки.
